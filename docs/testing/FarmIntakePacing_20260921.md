# 給水開閉と大会待ち時間の検証（2026-09-21）

このページは9/21時点の記録。現在のrunnerは正式作物を含む144ケースに拡張済み。[9/24の検証結果](FarmFormalSeasonBalance_20260924.md)を参照。末尾の「待ち時間短縮が未実装」は当時の状態であり、現在は時間送り機能が実装されている。

## 結論

30日間のSystemテストを36ケースから72ケースへ拡張した。追加した36ケースでは、じょうろを使わず、水路からの給水を開閉して6個の栽培・販売・出品・終了まで完走した。これは実機UIを人が操作した結果ではなく、一定間隔で判断するスクリプトの結果である。

この配置では流しっぱなしより給水を止めた方が高い得点になった。4倍速では判断間隔が長いと水分過多が増える場合がある。一方、最小限の6個だけを育てる経路では、倍率操作を簡単にしても大会待ちは長い。今回は測定だけで、ゲームの速度・価格・成長式・大会日程は変更していない。

## 再現と検証範囲

```powershell
cmd /c tools\tests\run_farm_season_balance_test.cmd
```

`farm_season_balance_test.cpp` が実際のToolAction / Irrigation / Growth / Date / Contest / Economy / Progression Systemsを呼ぶ。72ケース、`/O2 /W4 /WX` のコンパイルと実行が成功。条件違反は例外を捕捉し終了コード1で報告する。今回の実行ログは `generated/codex_checks/season_intake_20260921.txt`。

CSVの `irrigation_received` と給水あり/残留水収穫数は追加した開閉ルートだけの計測。既存ルートの0は未集計を表し、常時給水で実際の流量が0という意味ではない。

CSVの `irrigation_received` と給水あり/残留水収穫数は追加した開閉ルートだけの計測。既存ルートの0は未集計を表し、常時給水で実際の流量が0という意味ではない。

- 既存36ケース（2作物×手動/乾燥/常時給水×1/2/4倍×30日目提出/31日目期限終了）を維持。
- 開閉36ケース（2作物×確認間隔0.5/1/2秒×1/2/4倍×2終了方法）を追加。
- 既定ルール、5×4マス、300G、種0個、Day1開始。水源0→水路1→畑2。カブH0、ニンジンは水源・水路・畑ともH1。毎回植付け前に堆肥を使用。
- 各期間の初日に1マスで2個を順に育て、1個を保護・予約し、もう1個を売る。6個以上の栽培や土地作りで待ち時間を埋めない限定経路。
- 開閉ルートは初期に取水を閉じ、じょうろを一度も使わない。成長中、適量範囲の下から25％以下で開き、75％以上で閉じる。具体値はカブ32.5/57.5％、ニンジン46.25/68.75％。これは検証用の管理方針で、ゲーム内の自動制御機能ではない。
- 確認間隔は倍率適用前の固定1/60秒tickで数える。4倍・2秒おきならゲーム内8秒おきの確認。実際のCPU処理時間や人の反応時間を測ったものではない。
- 収穫判定は毎tickで行い、収穫直前に給水を閉じる。購入・植付け・堆肥・出品・選択・クリック時間は含まない。したがって実プレイの操作量/所要時間の下限寄りのモデルである。
- 水分・品質・所持金・日付の直接代入はなし。収穫後に残った土の水分もそのまま使う。追加給水のあった収穫と残留水だけで育った収穫を分けて記録する。

## 待ち時間

全提出時のDay30までの進行時間は1倍1740.05秒、2倍870.05秒、4倍435.05秒。案内停止や入力時間を除いた実時間換算であり、テストの実行に7分かかったという意味ではない。

4倍の開閉ルートは6個を育てる時間が15.48〜26.67秒相当、その畑に作物がない時間が408.38〜419.57秒相当。後者は全進行時間の約94〜96％。1マス・6個だけを作る経路なので、普通のプレイヤーが同じ割合で何もせず待つとは断定できない。ただし、必要な出品物を用意した後に待つ操作の改善は優先度が高い。

## 安全性の確認

既存の資金収支、購入/収穫6回、保護品の売却除外、重複/古い世代の提出拒否、大会案内中と終了後の時計停止を維持。毎tickで水量保存誤差、有限な水分/成長値、接続、計測配列の範囲、取水閉時の給水ゼロを検査する。給水計測spanはその場で読み、System更新をまたいで保持しない。成長時間＋非成長時間＝進行時間も確認。

固定tick上限と1作物の上限を維持し、無限待ちを拒否する。ゲーム本体、UI、保存形式、DX12のDescriptor/Barrier/Fence/VRAM所有権を変更しない。テスト中は既存System内部の履歴用動的確保などを利用するが、新たな実行時機能は追加していない。

## 検証方針の修正

初回案では開閉ルートにも植付け前のじょうろを使ったため、カブが一度も開操作なしで育ち、開閉の検証になっていなかった。最終測定はじょうろなしへ変更した。その後「毎収穫で追加給水が必須」という仮定が残留水で育つ実装と矛盾したため、給水あり/残留水のみの2分類に変更した。初回案の数値は上の最終結果に混ぜていない。
